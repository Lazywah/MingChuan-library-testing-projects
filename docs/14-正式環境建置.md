## 0. 先看這四件事

這四件是**在正式環境做錯會有後果**的，不是風格建議。

### 🔴 A. 不要複製開發機的 `.env`

`.env` 裡有 `SECRET_KEY`、資料庫金鑰、`BOOTSTRAP_ADMIN_PASSWORD`。
複製過來等於把開發機的密鑰帶進正式環境。

**一定要在這台機器上跑 `python scripts/setup_env.py` 重新產生。**

### 🔴 B. 不要帶開發機的資料庫

開發機的 `data/ai_platform.db` 裡有測試帳號、測試公告、測試的使用統計。
正式環境要一個**乾淨的**資料庫 —— 它會在第一次啟動時自己建好。

> 唯一需要從開發環境帶過來的是**組織對照表**，而它已經在版控裡：
> `config/org-mapping.json`（見 §5）。

### 🔴 C. 測試帳號的 email 一律用 `@example.com`

`@example.com` / `@invalid` 是 RFC 保留網域，`send_email` 有閘門擋著。

用真實網域（`@mail.mcu.edu.tw`）建測試帳號的話：**每次登入都會寄一封
login_alert**，反覆測介面就一封一封累積地寄給不存在的信箱。
開發機踩過兩次，總共真的寄出約 44 封必退信件。

### 🔴 D. 不要從主機端一般開啟 `data/ai_platform.db`

不要用 DB Browser、`sqlite3 data/ai_platform.db` 之類的方式打開它。
那會讓 Docker 容器**從此開不了那個檔**，一路噴 `unable to open database file`，
只能重啟才好（開發機因此製造過 235 次錯誤）。

要從主機看的話用唯讀模式：

```bash
python -c "import sqlite3;c=sqlite3.connect('file:data/ai_platform.db?mode=ro&immutable=1',uri=True);print(c.execute('select count(*) from users').fetchone())"
```

在容器裡查則沒有這個問題：

```bash
docker compose exec -T job-scheduler python -c "import sqlite3;print(sqlite3.connect('/data/ai_platform.db').execute('select count(*) from users').fetchone())"
```

## 1. 環境需求

| | |
|---|---|
| OS | Linux 或 Windows + Docker Desktop |
| Docker | 含 Compose v2（`docker compose` 不是 `docker-compose`） |
| GPU | NVIDIA driver + `nvidia-container-toolkit`（要跑訓練與 GPU 實驗室才需要） |
| Python | 3.9 以上（只有 `scripts/` 用得到，服務本身跑在容器裡） |
| 磁碟 | base images 很大，建議 100 GB 以上 |

驗證：

```bash
docker --version && docker compose version
docker run --rm --gpus all nvidia/cuda:12.4.0-base-ubuntu22.04 nvidia-smi
```

第二行跑不起來就是 GPU 沒接好 —— 平台仍然裝得起來，但訓練與 GPU 實驗室不能用。

## 3. 產生 `.env`

```bash
python scripts/setup_env.py
```

互動式，會問你：

- **管理員密碼** —— 寫進 `BOOTSTRAP_ADMIN_PASSWORD`，第一次啟動時自動建 `admin` 帳號
- SMTP、MYAI 廠商帳密等

> 留空管理員密碼 = 不會自動建 admin（之後要手動建，見 §6）。

### 3.1 手動貼上 SSO 憑證

`setup_env.py` **不會問也生不出來** —— 只有學校 IT 給得出來。
編輯根目錄的 `.env`：

```
OIDC_CLIENT_ID=<IT 提供>
OIDC_CLIENT_SECRET=<IT 提供>
```

> ⚠ **只貼值，同一行不要寫註解**。
> ⚠ 沒填 = SSO 停用 = **學生一個都無法登入**（admin 仍可從 :8888 進）。
> discovery / redirect_uri 已有正確預設，通常不用動。

MCU 用的是**自建 OIDC**（`auth.mcu.edu.tw`），不是 Microsoft Entra。

### 3.2 驗證

```bash
python scripts/setup_env.py --check
```

要看到「**✅ 無漂移**」。這一步會抓出「`.env` 少了新欄位」——
從舊版升上來時最容易漏。

## 6. 第一次登入管理端

### 6.1 🔴 管理端是對外開著的（2026-09-11 更新）

入口：<https://ai.lib.mcu.edu.tw:8888/>

> ⚠️ **這一節在 2026-09-11 之前寫的是「管理端只綁本機、區網也連不到」——
> 那已經不是事實了。** 2026-09-01 擁有者裁定「管理端對校內開放」
> （這台機器少有人到場，接手者需要從別台電腦管理），
> `docker-compose.yml` 的埠對應就從 `127.0.0.1:8888:8888` 改成了 `8888:8888`。
> 舊文字留著會讓接手的人以為它連不到，因而完全不會想到要保護它。

#### 現在實際的狀況

`nginx.conf` 的管理端 server 區塊宣稱有三道防線：

1. **TLS 強制** —— `listen 8888 ssl`，與使用者端同一張 Let's Encrypt 憑證
   （憑證不綁埠）。管理員帳密不會明文走網路。✅ 有效
2. **Windows 防火牆限校內** —— 規則「AI Base admin (campus only)」，
   限 `120.125.0.0/16` ＋私網段。🔴 **實際上沒有生效**（見下）
3. **帳密 ＋ 每次登入寄通知信** ✅ 有效

#### 🔴 第 2 道防線沒有生效（2026-09-11 實測）

Windows 防火牆的 **Allow 規則是疊加、不相減的** —— 只要有任何一條放行就通。
而 Docker Desktop 自己裝了一條：

| 規則 | Profile | Program | Port | Remote |
|---|---|---|---|---|
| `Docker Desktop Backend` | **Public** | `com.docker.backend.exe` | **Any** | **Any** |

聽 8888 的行程正是 `com.docker.backend.exe`（綁 `::`，全介面），
而對外網卡也正好在 **Public** 設定檔。沒有任何 Block 規則涵蓋 8888。
所以「campus only」那條允許的範圍早就被 Docker 那條涵蓋了，它沒有在限制任何東西。

這是 Docker Desktop 在 Windows 上有名的坑：**發布的埠由它自己的行程代理，
繞過以埠為單位的防火牆規則。**

而且這台**直接坐在公網 IP 上**（銘傳 `120.125.0.0/16`），不是在 NAT 後面。

#### 探測得到嗎 —— 被動就找得到

1. **憑證透明度日誌**：`ai.lib.mcu.edu.tw` 的 LE 憑證一簽發就公開登錄在 CT log
   （crt.sh 查得到）。列舉 `mcu.edu.tw` 子網域就會免費拿到這個主機名。
2. **8888 是掃描器的預設目標**：nmap top-1000 裡就有，Shodan / Censys
   全年無休掃遍整個 IPv4 的這個埠。
3. **憑證直接自證**：8888 回的是有效憑證，掃到的人立刻知道這是真的服務。
4. 開進去標題就是「管理員登入」。

#### 還沒驗證的一件事

**銘傳的校園邊界防火牆是否擋掉外部連入 8888，從這台機器看不到。**
如果它有擋，目前是被這台機器控制範圍以外的東西救著 —— 那不是上面那份
設計文件所宣稱的防線，也不該當成防線來依賴。

要確認很簡單：**手機關掉 Wi-Fi、用行動網路開 <https://ai.lib.mcu.edu.tw:8888/>**。
開得起來就是真的對外開著。

#### 狀態

**擁有者 2026-09-11 裁定暫不更動。** 這一節是把現況寫清楚，不是待辦。
真要收斂的話，方向依序是：

| 方法 | 說明 |
|---|---|
| 綁 Tailscale 位址 | `docker-compose.yml` 改成 `<Tailscale IP>:8888:8888`。這台已裝 Tailscale，管理者人數是個位數，可行。改完 8888 就徹底不在公網上。 |
| 請校方 IT 在邊界擋 | 把控制放到真正管用的地方。可與上一項併用。 |
| ~~改 Docker 的防火牆規則來源範圍~~ | 🚫 **不要**。Docker Desktop 更新或重啟會重寫自己的規則，這種修法會無聲失效，而失效時看起來跟正常一模一樣。 |

> 📌 登入連續失敗或一直重新整理會撞到速率限制（`/auth/login` 是 **10 次/分鐘**），
> 回 429 而不是 401。**等一分鐘再試**，不要以為是帳密錯了或服務掛了。

## 8.5 網路與跨校區

三件事的答案不一樣，分開處理。

### 8.5.1 學生怎麼連到平台（校內 + 跨校區）

這是**一件事**，不是兩件 —— 平台只要有一個**校內 DNS 解得到的名字**，
桃園與台北的學生就一樣連。

| 要的東西 | 誰做 |
|---|---|
| 校內 DNS 名稱（如 `aibase.mcu.edu.tw`） | **IT** |
| TLS 憑證（該名稱的） | **IT** |
| nginx 的 443 區塊 | 見 §8.5.2（設定檔裡目前**沒有**任何 `listen 443`） |

> 🔴 **先問 IT 一個問題**：台北的學生電腦**連不連得到**桃園這台的 IP？
> 那是既有的網路架構，平台這邊決定不了，而答案會決定後面全部：
> - **通** → 只要 DNS + TLS 就好
> - **不通** → 要走 VPN，或把平台放到 DMZ（那是 IT 的決定）

### 8.5.2 上 TLS（拿到憑證之後）

把憑證放到主機上，例如 `infrastructure/certs/`，然後：

**(1) `docker-compose.yml` 的 nginx 服務加 443 與憑證掛載**

```yaml
    ports:
      - "80:80"
      - "443:443"                     # ← 加這行
      - "8888:8888"                   # ⚠ 對外開著，不是只綁本機（見 §6.1）
    volumes:
      - ./infrastructure/certs:/etc/nginx/certs:ro    # ← 加這行
```

**(2) `infrastructure/nginx.conf` 加一個 443 的 server 區塊**

⚠ **照著 `listen 80` 那個區塊複製**，只改最上面四行。
🔴 **`set $scheduler` 那一行一定要保留** —— 後端位址放在**變數**裡是為了讓
nginx 每次請求重新解析 DNS。寫成固定的 `proxy_pass http://job-scheduler:8000`
會讓 nginx **快取住舊的 container IP**，於是重啟 job-scheduler 之後全站 502
（2026-08-27 稽核修掉的就是這個）。

```nginx
    server {
        listen 443 ssl;
        http2 on;
        server_name aibase.mcu.edu.tw;          # ← 換成正式名稱

        ssl_certificate     /etc/nginx/certs/fullchain.pem;
        ssl_certificate_key /etc/nginx/certs/privkey.pem;
        ssl_protocols       TLSv1.2 TLSv1.3;

        # ZH: 後端位址放變數 → 每次請求重新解析（理由見檔案上方註解）
        set $scheduler "http://job-scheduler:8000";

        # ── 以下把 `listen 80` 那個 server 區塊裡的所有 location 原封複製過來 ──
        # ⚠ 不要「只複製 /api/」—— 前端的靜態檔 location 也要，
        #   不然 https 進來只拿得到 API、開不了頁面。
    }
```

**(3) 把 :80 改成轉址（可選但建議）**

```nginx
    server {
        listen 80;
        server_name aibase.mcu.edu.tw;
        return 301 https://$host$request_uri;
    }
```

> ⚠ 改成轉址之後，**用 IP 直接連的路就斷了**。先確認 DNS 通了再改，
> 不然會把自己鎖在外面。

**(4) 驗證**

```bash
docker compose up -d nginx
curl -sI https://aibase.mcu.edu.tw/api/health | head -1     # 要 200
curl -sI http://aibase.mcu.edu.tw/ | head -1                # 若做了轉址，要 301
```

### 8.5.3 台北的 30 台 GPU（比想像中簡單）

**worker 是純拉取式** —— 它主動 `POST` 到桃園要工作
（`/worker/take`、`/heartbeat`、`/jobs/{id}/update`），桃園不會主動找它。

| 問題 | 答案 |
|---|---|
| 台北要開 inbound 防火牆規則嗎？ | ❌ **不用** |
| 跑工作需要 VPN 嗎？ | ❌ 不用（只要台北**連得到**桃園的 `:8002`） |
| 台北的機器要固定 IP 嗎？ | ❌ 不用 |

#### 🔴 真正的瓶頸是映像頻寬，不是連線

單一個訓練映像約 **20 GB**，30 台各拉一次 = **600 GB 跨校區流量**。

**先分清楚 compose 裡的兩個 registry —— 它們不是同一件事**

| profile | 是什麼 | 放什麼 | 能不能推 |
|---|---|---|---|
| `registry` | 私有 registry（htpasswd 帳密） | **我們自己建的 `aibase/*`** | ✅ 要推 |
| `registry-cache` | Docker Hub 的 pull-through 快取 | 公開映像（`python:3.11` 這種） | ❌ 只能拉 |

`aibase/*` 不在 Docker Hub 上，所以 **cache 對它一點幫助都沒有** ——
那是 `registry` 的事。反過來，公開映像不需要推，那是 `registry-cache` 的事。

> 🔴 **實測結論（2026-09-23）：pull-through cache 不能代理我們的私有 registry。**
> 「台北放一台 cache、上游指著桃園的 registry」這條看起來最漂亮的路**是死的**：
> registry:2 的 proxy 會先 ping 上游 `/v2/` 拿到 Basic 認證的 challenge，
> 但**接下來的 manifest 請求不帶任何認證**，上游回 401，
> 使用者看到的是 `manifest unknown`（上游 log 才看得到真正的 401）。
> `REGISTRY_PROXY_USERNAME/PASSWORD` 只對 **token（Bearer）型**的上游有效，
> 也就是 Docker Hub 那一類 —— 所以 compose 裡那兩個變數叫 `DOCKERHUB_*`。
> 已在本機用一個臨時 proxy 容器對著 `--profile registry` 驗過，確定會這樣壞。

**可行的做法：台北自己跑一台真的 registry，桃園推一次過去。**
跨校區流量＝**每個映像 1 次**（不是 30 次），30 台從台北本地拉。

```bash
# ── 台北那台（跑 registry 的機器）
#    1. 在它的 .env 填 REGISTRY_USERNAME / REGISTRY_PASSWORD（密碼至少 12 字元）
bash infrastructure/registry/make-htpasswd.sh
#    2. 要讓另外 29 台連得到，所以不能只綁 127.0.0.1
REGISTRY_BIND=0.0.0.0 docker compose --profile registry up -d registry

# ── 桃園（服務層，映像是在這裡建的）
docker login <台北主機>:5000 -u <帳號>          # 密碼用 --password-stdin 餵，不要寫在指令裡
IMAGE_REGISTRY_PREFIX=<台北主機>:5000 bash infrastructure/base-images/push-all.sh

# ── 那 30 台 worker 的 env（start-worker.sh 讀的那一份）
IMAGE_REGISTRY_PREFIX=<台北主機>:5000
REGISTRY_USERNAME=... / REGISTRY_PASSWORD=...   # worker 開機會自己 docker login
```

⚠ **明文 HTTP 的話，那 30 台的 docker daemon 都要設 `insecure-registries`**，
否則 `docker pull` 直接拒絕。要免掉這一步就讓 registry 走 nginx 的 TLS（見 §8.5.2）。

⚠ worker 只會把 **`aibase/` 開頭**的映像名改寫成 `<prefix>/aibase/...`
（`worker.py::resolve_image`）。公開映像仍然直接找 Docker Hub ——
那部分要省流量／避開 Hub 的速率限制，才是 `registry-cache` 上場的地方
（台北起一台，daemon 設 `registry-mirrors`）。

<details>
<summary>2026-09-23 在桃園這台實測過什麼（點開）</summary>

| 驗了什麼 | 結果 |
|---|---|
| `make-htpasswd.sh` → `--profile registry` | 匿名 `/v2/` 回 **401**，帶帳密回 **200** |
| push `aibase/code-server:2026-spring` → 刪掉本機 tag → pull 回來 | digest 一致 |
| worker 容器內 `registry_login()` | **True**（`docker login` 走 stdin，密碼不進命令列） |
| worker 的 `resolve_image()` | `aibase/*` 補前綴、公開映像原樣、已帶前綴的不重複套 |
| `registry-cache` 對 Docker Hub 回源 | 第一次每個 blob **760–773 ms**；第二次同樣的 blob **1–2 ms**，3.6 MB 的層 **2.25 ms** |
| `push-all.sh` 的映像清單推導 | 9 個（含 `code-server-gpu`，見下） |

⚠ **沒有驗過的**：整套 9 個映像的完整推送（約 170 GB）、跨校區的真實頻寬與耗時、
以及 Windows 節點上的行為。上面那些是機制對不對，不是規模夠不夠。

🔴 順帶抓到的坑：`push-all.sh` 原本漏推 `code-server-gpu` ——
而 `lab_manager` 的 `default_gpu_image` 正是它。GPU 節點獨立之後，
症狀會是「CPU 實驗室好好的，GPU 實驗室永遠起不來」。
已改成從 `build-all.sh` 的 `docker build -t` 一併推導，不再手寫特例清單。

</details>

> ⚠ 台北那 30 台是**全 Windows**。worker 跑得起來（這是現況不是問題），
> 但 base image 的建置與快取要照 Windows 的方式處理。

> ⚠ 這條線**與 SSO 無關，也不擋 SSO** —— 可以等學生登得進來之後再做。

## 9. SSO go-live 的三項（需要 IT 配合）

程式碼都好了，缺的是**非程式**的東西。

### 9.1 順序不能顛倒

```
① 決定正式主機名  ──┐
                    ├→ ③ 回報 IT 加進白名單 → ④ 學生才登得進來
② 申請 TLS 憑證  ──┘
```

🔴 **主機名之後要改的話，②③ 都要重來** —— IT 那邊的白名單也要重加。
所以名字要**一次定案**。

### 9.2 `.env` 要改的

`.env.example` 裡的預設是開發用的：

```
OIDC_REDIRECT_URI=http://localhost/api/v1/sso/oidc/callback
```

正式的長這樣（**用 https、用正式主機名**）：

```
OIDC_REDIRECT_URI=https://aibase.mcu.edu.tw/api/v1/sso/oidc/callback
```

> 🔴 **要 https 不要 http。** OIDC 的 authorization code 走 redirect_uri 回來，
> 明文傳等於把登入憑證放在網路上；而且很多 IdP 直接**拒絕**非 https 的
> redirect_uri。

改完 `.env` 要 `docker compose restart job-scheduler`（`.env` 不是即時生效的）。

### 9.3 跟 IT 溝通時

> ⚠ MCU 用的是**自建 OIDC**（`auth.mcu.edu.tw`），**不是 Microsoft Entra**。
> 兩者的申請流程不一樣，講錯會來回好幾趟。

`docs/IT-OIDC-申請信範本.md` 有現成的信可以改。

### 9.4 沒做完會怎樣

| 缺哪一項 | 症狀 |
|---|---|
| `OIDC_CLIENT_ID` 沒填 | SSO **靜默降級成 mock** —— 看起來能登入，但那是假的 |
| redirect_uri 沒進白名單 | 學生按登入 → IdP 直接拒絕 |
| 只有 http 沒有 https | IdP 可能拒絕；就算通了也是明文傳憑證 |

## 10. 出事的時候

| 症狀 | 先看 |
|---|---|
| 整站 502 | `docker compose ps`，job-scheduler 是不是掛了 |
| 學生登不進來 | `.env` 的 `OIDC_CLIENT_ID` 有沒有填、redirect_uri 有沒有進 IT 白名單 |
| 改了 `.env` 沒生效 | `.env` 要**重啟**才吃；系統設定頁的旋鈕才是即時的 |
| 前端沒更新 | 改過 JS/CSS 要 `python scripts/bump_assets.py` |
| 資料庫開不了 | 是不是有人從主機端一般開啟了 `.db`？重啟 job-scheduler |
| 借不到 GPU | `nvidia-smi` 確認卡在；管理端 → 平台設定 → GPU 節點看時段設定 |

日常維運見 [04-operations.md](04-operations.md)。

## 11. 給在這台機器上作業的 Claude Code

如果你是接手這份文件的 AI：

1. **不要跳過 §0 的四條**。那四條每一條都在開發環境真的發生過。
2. **每一步都驗證，不要假設**。這份文件每一節都給了驗證指令，跑它。
3. **`.env` 與資料庫不要從別處複製**（§0 A、B）。
4. 建測試帳號時 email 一律 `@example.com`（§0 C）。
5. 需要人決定的事**停下來問**，不要自己選：
   - `myai_initial_credit` 給多少
   - `login_alert_email` 要不要開
   - 告警信寄給誰
   - 正式主機名與 redirect_uri
6. 改了任何前端檔案要跑 `python scripts/bump_assets.py`，
   改了後端要 `docker compose restart job-scheduler`。
7. 宣稱完成之前，把 §8 的清單逐項跑過。
