## 0. 現況

```
送單 jobs.py:86 ─→ pending(SQLite)
  ↓
worker 每 5s 問 nvidia-smi ─→ POST /take（UPDATE … WHERE status='pending' 原子搶）
  ↓
execute_job：下載資料集(HTTP) → sha256 → 解壓 → docker run --rm
  ↓
每一行 stdout ─→ POST /update ─→ append_job_log（整欄讀出→接字串→commit）
  ↓
使用者端 SSE 每 1s refresh 整列 ─→ 完成：upload_artifact → status=completed

背景：逾時迴圈把 running 超過 job_timeout_minutes 的標成 failed
```

**架構的形狀是對的。** 原子搶單、實驗室與訓練雙向互斥（`crud.gpus_held_by_labs` ∪
`gpus_running_jobs`）、三個提早 return 都記得放 GPU 旗標、掛載收窄到單張任務 ——
這些難的地方都做對了，兩個方案都不動它們。

現行資料量：5 張單、最長 101 行 log。**下面沒有一項是今天壞掉的**，
全部是 30 台節點上線之後才會現形。

## 1. 方案一：補洞

| 代號 | 症狀 | 何時現形 | 改動 |
|---|---|---|---|
| **A** 🔴 | 跑起來的容器停不下來（取消只准 pending、逾時只改 DB、狀態機無守衛） | 第一個誤送的大任務 | 小 |
| **B** 🔴 | 每行 log 一趟同步 HTTP；伺服端整欄重寫 → O(n²) | 學生開始用 tqdm | 中 |
| **C** 🟡 | `max_concurrent_jobs: 4` 是**全叢集**上限且在送單時擋 | 30 台上線當天 | 小 |
| **D** 🟡 | 同機也走 HTTP 傳資料集，且每次都傳（快取只省解壓） | 資料集變大時 | 中 |
| **F** 🟡 | 映像沒預拉，冷拉時間算進逾時 | 30 台首次開機 | 小 |

### A — 停不下來（三件事同一個洞）

- 取消只准 `pending` / `queued`（[jobs.py:400](../job-scheduler/app/routers/jobs.py)）
- 逾時只把 DB 標 failed（[scheduler.py:66](../job-scheduler/app/scheduler.py)），
  worker **沒有任何 stop/kill 路徑**（全檔 grep 零筆）→ 容器繼續跑、卡繼續被佔，
  而服務層已不把它算進 `gpus_running_jobs` → **實驗室借得到那張正在訓練的卡**
- `update_job_status`（[crud.py:717](../job-scheduler/app/crud.py)）沒有終態守衛 →
  殭屍跑完回報 completed，把 failed 翻回來、蓋掉 `completed_at`

補法：`docker run --name job-<id>`；`/update` 的回應帶 `{"action":"stop"}`；
worker 收到就 `docker stop`；取消端點放行 running；`update_job_status` 拒絕終態回退。

### B — 日誌成本

worker 端每讀一行就 `report_update`，同步、timeout 5s、重試三次退避 2/4/6
→ 最壞一行卡 17 秒。卡住時 stdout 管線（64KB）會滿，**訓練程式自己被 print 擋住**。

服務端 `append_job_log`：SELECT 整列（含整段 logs TEXT）→ 字串相接 → commit(fsync)
→ 再 SELECT。單張單總成本 **O(n²)**。

補法：worker 批次（每 1s 或每 50 行一個 POST）；服務端改 append-only。

### C — 配額

`scheduler_policy.yaml` 的 `max_concurrent_jobs: 4` 在 [jobs.py:112](../job-scheduler/app/routers/jobs.py)
被當成整個叢集的 running 上限，學生超過就 429。
**30 台上線那天會有 26 台因為這一行空著**，畫面上只看得到學生一直被拒絕。

### D / F

見上表。D 的重點是「快取鍵在下載**之後**才算得出來」；
F 的重點是 `started_at` 在搶單那一刻就寫下，冷拉映像的時間算進逾時。

## 2. 方案二：換成標準的控制模型

方案一是「把看到的洞補起來」。方案二的差別是：**這些洞在文獻裡都有對應的標準解，
而標準解通常一次解掉好幾個洞，並且順手擋掉我們還沒想到的那些。**

### 2.1 租約（lease）＋ 執行世代（fencing token）

**現況的問題比 A 大**：逾時是「跑超過 N 分鐘就算死」——
一個合法的三小時訓練會被砍掉，而一台當機十秒的機器卻要等 120 分鐘才被發現。
兩種錯都來自同一件事：**我們用「跑多久」猜「還活著嗎」。**

文獻的做法（分散式排程器的通用模式）：

- `/take` 時發一個**租約**與一個 `execution_id`（世代編號）
- worker 每 N 秒續租；**續不上才算死**，與跑多久無關
- 回收器只看 `lease_until < now`，把單子重新排入
- 🔴 **fencing**：每一次 `/update` 都要帶 `execution_id`，
  服務層比對不符就回 **409 STALE_EXECUTION**

最後那一條正是 A 的第三件事（殭屍翻回 completed）的標準答案，
而且它同時擋掉「同一張單被兩個節點各跑一份」時的錯亂寫入 ——
那個情境現在不會發生（原子搶單擋住了），但租約回收機制一旦引入就會發生。

> 「A zombie worker—one that froze on a long garbage collection pause, lost its
> lease, and then woke up and tried to finish writing results—is solved by a
> fencing token: the datastore rejects any write carrying an older token.」

**對我們的意義**：`job_timeout_minutes` 從「業務規則」降級成「最長容許執行時間」
（那仍然該有，但它是政策不是健康檢查）。節點當機的偵測從 120 分鐘縮到一分鐘內。

### 2.2 指令通道：回報的**回應**就是指令

Buildkite agent 的架構是最貼近我們的先例（同樣是 pull-based、同樣跑別人的程式）：
每個 JobRunner 起三條並行的東西 —— Job Process、Log Streamer、
**Job Cancellation Checker（專門輪詢取消狀態）**。

我們不必另開一條輪詢：`/update` 本來就每隔一段時間打一次，
**讓它的回應帶回指令**（`stop` / `nothing`）即可。方案一的 A 已經提到這個做法，
文獻確認它是標準結構而不是臨時發明。

### 2.3 日誌：drain → chunk → append-only

三個獨立的修正，文獻各有對應：

1. **worker 端把 drain 與上傳拆開。** 開一條執行緒只負責把 stdout 讀進
   本地環形緩衝／輪替檔案，**永不因為網路而阻塞**；另一條批次上傳。
   > 「Training progress must not depend on the presence or lifetime of a
   > log-streaming client... start a client-independent drain when the process
   > launches (bounded ring buffer or rotating file).」

   這正是我們現在的病：網路慢 → 上傳卡住 → 管線滿 → **訓練本身變慢**。

2. **分 chunk 併發上傳**（Buildkite LogStreamer 的做法，預設 3 條上傳 worker）。

3. **服務端 append-only**：`job_logs(job_id, seq, text)` 一列一筆，
   不要在 TEXT 欄位上做字串相接。
   > 「Append-only facts... avoids expensive row rewrites since each entry is immutable.」

**順帶修好 SSE**：現在 `stream_job_logs` 每秒 `db.refresh` 整列、斷線重連從頭 replay。
改成 cursor + `Last-Event-ID` 之後，重連只補沒收到的部分。

### 2.4 配額：把「准不准進場」與「放在哪張卡」分開

這是 Kubernetes 生態最清楚的一課：**Kueue 管 quota 與 admission，
Volcano / KAI 管 placement**，兩者是不同層。

我們現在把兩件事混在**送單**那一刻做（`max_concurrent_jobs` 在 submit 時擋），
結果是：既不能反映叢集真實狀態（4 是寫死的），
也不能排隊（超過就 429 請使用者自己重試）。

方案二：
- **送單一律收下**，進佇列（使用者看到的是「你排第 7 位」而不是 429）
- **派工時**才看配額：每人上限、每角色上限、叢集上限三層
- 配額是**佇列的屬性**，不是送單的閘門

這樣 30 台不會因為一行設定空著，學生也不會看到一個他無法理解的錯誤。

### 2.5 🔴 GPU epilog —— 方案一完全沒想到的一項

Slurm 在共享 GPU 叢集上的標準做法是 prolog / epilog，
而 epilog 的典型工作是「刪暫存、殺殘留 process、**重設 GPU 狀態**」：

> 「A job that crashes can leave a GPU in a bad state, and an epilog that resets
> the device turns a mysterious recurring failure into a non-event.」

我們的 `docker run --rm` 清得掉容器，**清不掉卡的狀態** ——
殘留的 compute process、沒釋放的 VRAM、ECC 錯誤。
單機時這種事人在旁邊看得到；**30 台無人值守的機房裡，症狀會是
「某一台從此每一張單都失敗」而沒有人知道為什麼。**

具體做法：任務結束後 worker 執行一段 epilog ——
`nvidia-smi` 確認該卡 VRAM 歸零、沒有殘留 process；
異常就**把節點標成 unhealthy 並停止領工**，同時發告警。
這比「等使用者回報」早幾天發現問題。

> ⚠ 這一項在方案一裡完全不存在。它不是效能優化，是**無人機房的必需品**。

### 2.6 映像與資料集的分發

30 台同時拉一個 22GB 的映像 = 660GB 走同一條線、打同一個 registry。
業界答案是 P2P 分發（Dragonfly 是 CNCF 畢業專案；Uber 的 Kraken 在
尖峰時 30 秒內分發 20K 個 100MB–1G blob）：

> Dragonfly 在 200 節點的叢集上把模型分發的回源流量從 26 TB 降到約 130 GB。

**但對 30 台而言 P2P 很可能過重。** 折衷順序：
1. 先做**預拉**（方案一的 F）與**本地 mirror registry**
2. 量出實際的拉取時間之後，再決定要不要上 Dragonfly

資料集同理，但方向不同：改成**內容定址的 manifest**，
`/take` 就把 digest 送給 worker，**先比對本地快取再決定要不要下載**
（現在是先下載完才算得出雜湊）。文獻的說法是
「pull 成功本身就是節點持有正確資料的證明」。

### 2.7 資料庫：明確**不要**換

順手把這件事釘住，免得日後有人把「效能」直覺地等同於「換 Postgres」。

- SQLite 的 WAL **不提供並行寫**，寫入仍然序列化；
  換 Postgres 的門檻是「每秒數千筆跨行程寫交易」
- 我們的量：30 台 × 心跳/30s ≈ **1 write/s**；
  log 批次化之後再加幾筆/秒
- 結論：**SQLite 綽綽有餘**。前提是 2.3 做完 ——
  現行「每行 log 一次 commit」才是真正危險的那個寫入模式

## 3. 兩案對照

| | 方案一 | 方案二 |
|---|---|---|
| 性質 | 補洞 | 換控制模型 |
| A 停不下來 | 加 stop 指令 + 終態守衛 | 租約 + 世代 + 指令通道（連帶解決逾時誤判） |
| B 日誌 | 批次 + append-only | 再加：獨立 drain（訓練不再被網路拖慢）、SSE cursor |
| C 配額 | 改成 per-user、移到派工端 | admission 與 placement 分層，送單改成排隊 |
| D/F 分發 | 預拉 + 先比對 digest | 同左，並評估 mirror / P2P 的門檻 |
| GPU 健康 | — | **epilog 檢查 + 自動停止領工** |
| 資料庫 | 沒提 | 明確結論：不換 |
| 工作量 | 小（數天） | 中（一到兩週） |
| 風險 | 低，改動局部 | 中，動到派工與回報的契約 |

## 4. 建議順序

1. **A + C**（方案一版本）—— 正確性與 30 台上線的阻塞點，改動小，可以當天驗完
2. **2.5 GPU epilog** —— 無人機房必需，與 A 同一個位置（任務結束路徑），一起做最省
3. **B** —— 上線前做完；先量再決定要做到哪一步（純批次 vs 完整 drain）
4. **2.1 租約 + 世代** —— 取代逾時猜測，建議在 30 台實際跑起來之後再做，
   那時才有真實的當機樣本可以驗
5. **D/F、2.6** —— 效率，最後做

⚠ 本文所有效能主張都是靜態分析。**動工前先補一支壓測腳本**
（模擬 N 張單 × 每秒 M 行 log），否則無從判斷 B 到底該做到哪一步。
